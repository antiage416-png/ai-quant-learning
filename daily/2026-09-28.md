## 2주차 10일차: 주소·날짜·공백 정리

### 실습한 내용
- normalize_article.py에서 예시 문자열을 정리했다.
- urljoin으로 /article/1을 https://example.com/article/1로 변환했다.
- strptime으로 날짜 문자열을 해석하고 strftime으로 YYYY-MM-DD 형식으로 변환했다.
- split과 join으로 연속 공백·줄바꿈·탭을 공백 하나로 정리했다.
- 인터넷 요청 없이 실행했다.

### 배운 점
- /로 시작하는 상대주소는 사이트의 루트 경로를 기준으로 한다.
- / 없이 시작하는 상대주소는 기준 페이지의 디렉터리를 기준으로 한다.
- / 유무에 따른 비교는 설명으로 이해했으며 별도 실행하지 않았다.
- strip은 앞뒤 공백만 제거한다.
- " ".join(text.split())은 내부 공백도 정리한다.

### 오류와 해결
- 실제 파일 이름이 nomalize_article.py여서 실행 경로와 달랐다.
- 파일 이름을 normalize_article.py로 수정한 뒤 정상 실행했다.

### 결과물
- exercises/normalize-day10/normalize_article.py

## 3주차 15일차: HTTP 오류·연결 오류·타임아웃 처리

### 실습과 검증
- 없는 페이지에 요청해 HTTPError로 404 처리.
- 유효하지 않은 도메인에 요청해 URLError로 주소 해석 실패 처리.
- 로컬 서버는 3초 뒤 응답하고, 클라이언트는 timeout=1로 요청.
- 두 번째 터미널에서 타임아웃 안내와 종료 문구 확인.

### 배운 점
- try는 오류가 발생할 수 있는 작업을 실행한다.
- except는 지정한 종류의 오류가 발생했을 때 실행된다.
- HTTPError는 URLError의 하위 종류이므로 먼저 처리한다.
- 서버의 200 기록만으로 클라이언트의 수신 성공을 판단할 수 없다.
- 타임아웃은 클라이언트 터미널의 결과로 확인했다.
- timeout은 전체 프로그램의 실행 시간 제한과는 다르다.

### 실행 시 주의점
- 현재 handle_errors.py는 로컬 주소와 timeout=1로 설정되어 있다.
- slow_server.py를 먼저 실행한 뒤 다른 터미널에서 요청해야 한다.
- 서버는 요청 한 번을 처리한 뒤 종료된다.

## 3주차 16일차: 429 응답과 제한된 재시도

### 실습
- 로컬 연습 서버와 클라이언트를 별도로 작성.
- 첫 요청에 429와 Retry-After: 2를 반환하도록 설정.
- 클라이언트가 2초 기다린 후 재요청하여 200으로 성공하는 흐름 확인.
- 서버가 처음 10회 요청에 429를 반환하도록 변경.
- 클라이언트가 총 3회 시도 후 종료하는지 확인.

### 배운 점
- Retry-After는 재요청 전에 기다릴 시간을 알려주는 응답 헤더다.
- 클라이언트가 헤더를 읽고 time.sleep으로 기다린다.
- 최대 시도 3회는 첫 요청 1회와 재시도 최대 2회를 뜻한다.
- 성공하면 break로 반복을 종료한다.
- timeout은 네트워크 작업의 대기 제한이고,
  sleep은 다음 요청 전에 의도적으로 쉬는 시간이다.

### 현재 구현 범위
- 429와 초 단위 Retry-After에 대해서만 재시도한다.
- 날짜 형식 Retry-After나 헤더가 없는 경우는 종료한다.
- 연결 오류와 타임아웃은 재시도하지 않는다.
- 기존 명언 수집 코드에는 아직 통합하지 않았다.

### 추가 실험: 서버와 클라이언트의 요청 횟수

- max_attempts를 11로 변경해 실험했다.
- 서버를 재시작하지 않았을 때는 이전 요청 3회가 누적되어,
  새 클라이언트의 8번째 요청에서 성공했다.
- 서버를 재시작한 뒤에는 10회 거절되고 11번째 요청에서 성공했다.
- 서버의 누적 요청 수와 클라이언트의 실행별 시도 횟수는 별개다.
- max_attempts는 반드시 실행할 횟수가 아니라 최대 시도 횟수다.
